## 1. Onde estamos no compilador
- **Gerar código** = produzir um programa **equivalente** ao fonte na linguagem da máquina-alvo.
	- Entrada : árvore/ações da análise + **tabela de símbolos**. Saída : código objeto (aqui, montagem da máquina de pilha).
- Tarefas : (1) reservar espaço para variáveis e registros de ativação; (2) selecionar instruções; (3) alocar registradores (o mais difícil — **desaparece** na máquina de pilha); (4) ordenar a avaliação.
- Na cadeira : **tudo nas ações semânticas do BYACC/J, numa única passagem**. Pulamos código intermediário e otimização.

### 1.1 Representação intermediária (RI)
- Separa front-end (linguagem) de back-end (máquina) : `m + n` tradutores em vez de `m × n`.
- Níveis : **alto** (`t1 = a[i, j+2]`, mantém subscritos/laços) → **médio** (código de 3 endereços, endereços explícitos) → **baixo** (registradores, `[fp - 4]`).
- Formas de `x := a + b * c` :
```code
AST            3 endereços       Pilha          Bytecode JVM
  :=           t1 = b * c        LDA _a         iload_1
 x   +         t2 = a + t1       LDA _b         iload_2
    a  *       x  = t2           LDA _c         iload_3
      b c                        MUL            imul
                                 ADD            iadd
                                 STA _x         istore 4
```
- **Quantos endereços por instrução?** Acumulador (1), registradores (2–3), **pilha (0)** — operandos implícitos no topo.
- **Por que pilha em uma passagem?** A ordem das reduções do LR **é a pós-ordem** → cada ação emite o código do operador **depois** do código dos operandos. Composicional (`código(E1) · código(E2) · ADD`), sem registradores, sem construir a árvore.

## 2. Ambiente de execução
### 2.1 Organização da memória
```code
endereços altos   ┌──────────────┐
                  │   Pilha      │ ← registros de ativação (locais, parâmetros)
                  │     ↓        │
                  │     ↑        │
                  │   Heap       │ ← new / malloc
                  │ Dados estát. │ ← globais, static, constantes (DS)
endereços baixos  │   Código     │ ← instruções
                  └──────────────┘
```
- **Escopo** = onde o nome pode ser usado no texto (estático). **Tempo de vida** = quando a variável existe na execução (dinâmico).
- Locais precisam de **um espaço novo a cada chamada** — é isso que permite **recursão**. *Pilha ≠ heap.*

### 2.2 Endereço de elemento de arranjo
- 1 dimensão : `&v[i] = base + w · i` (`w` = tamanho do elemento).
- 2 dimensões, por linhas (C, Pascal), `array[L1..U1, L2..U2]` :
$$\&a[i,j] = base + w\cdot\big((i-L_1)\cdot(U_2-L_2+1) + (j-L_2)\big)$$
- Exemplo : `B : array[5..8, 6..7] of integer` → `&B[8,6] = B + 4·((8−5)·2 + 0) = B + 24`.
- Os termos constantes podem ser pré-calculados na compilação.

### 2.3 Registro de ativação (quadro, *stack frame*)
**Quando e por quê?** Sempre que há subprogramas que podem estar **ativos mais de uma vez ao mesmo tempo** (recursão). Endereços fixos (como os globais) não funcionam : **cada ativação precisa da sua cópia** de parâmetros e locais. Um registro é **criado no topo da pilha a cada chamada e descartado no retorno**; um registrador **BP** aponta para o quadro corrente, e tudo é acessado por **deslocamento fixo em relação ao BP**, conhecido na compilação.
```code
          │ temporários         │ ← SP
 BP+2     │ local a             │  montado pelo CHAMADO (AMEM k)
 BP+1     │ local x             │
 BP+0     │ BP anterior         │  link dinâmico (PUSHBP · SETBP)
 BP−1     │ end. de retorno     │  JSR
 BP−2     │ último parâmetro    │  empilhado pelo CHAMADOR
 BP−3     │ 1º parâmetro        │
```
- Locais : `BP+1 … BP+k`. Parâmetros (n deles) : o i-ésimo fica em **`BP − (n − i + 2)`** (empilhados da esquerda p/ a direita).
- **Link estático** (Pascal, procedimentos aninhados) aponta para o quadro do procedimento que *contém* o atual no texto; C não precisa.

### 2.4 Sequência de chamada & retorno
```code
CHAMADOR                    CHAMADO (_p)
<código de e1> … <en>       _p:  NOP
JSR   _p                         PUSHBP      ; salva BP do chamador
DMEM  n   ; tira os args         SETBP       ; BP ← SP
                                 AMEM  k     ; locais
                                 <corpo>
                                 DMEM  k
                                 POPBP       ; restaura BP
                                 RTS         ; volta
```
*Simetria : cada passo da entrada é desfeito, em ordem inversa, na saída.*

### 2.5 Passagem de parâmetros
| Mecanismo | O que passa | `inc(a)` com `a=1` | Na máquina de pilha |
|---|---|---|---|
| valor | cópia | `a` continua 1 | chamador : `LDA _a` ; chamado : `LDO/STO` |
| referência (`var`) | endereço | `a` vira 2 | chamador : `LDC _a` ; chamado : `LDO k · LDI` / `STI` |
| valor-resultado | copia na entrada e na saída | 2 (no retorno) | — |
| nome | o texto, reavaliado a cada uso | 2 | — |

## 3. A máquina de pilha
- Registradores : **PC**, **SP**, **BP**. Nenhum registrador de dados.
- Operação binária : desempilha **RT1** (topo) e **RT2**, empilha **RT2 op RT1** → `LDA _a · LDA _b · SUB` = `a − b`.
- Booleanos : 0 = falso, ≠ 0 = verdadeiro.

| Instrução             | Efeito                                |     | Instrução                       | Efeito                    |
| --------------------- | ------------------------------------- | --- | ------------------------------- | ------------------------- |
| `DS N`                | reserva N bytes                       |     | `JMP N`                         | desvia                    |
| `LDC N`               | empilha constante (rótulo = endereço) |     | `JZER N`                        | desempilha; se 0, desvia  |
| `LDA N`               | empilha conteúdo de N                 |     | `JSR N` / `RTS`                 | chama / retorna           |
| `STA N`               | desempilha em N                       |     | `AMEM N` / `DMEM N`             | aloca / libera N palavras |
| `LDI` / `STI`         | indireto (endereço na pilha)          |     | `PUSHBP` `SETBP` `POPBP`        | encadeiam quadros         |
| `ADD SUB MUL DIV MOD` | aritmética                            |     | `LDO N` / `STO N`               | lê/escreve em BP+N        |
| `GRT LES EQ`          | relacionais (1/0)                     |     | `DUP` `DROP` `OUT` `HALT` `NOP` | —                         |

**Executando à mão `a := 3 + 4 * 5`** : `LDC 3 [3]` · `LDC 4 [3 4]` · `LDC 5 [3 4 5]` · `MUL [3 20]` · `ADD [23]` · `STA _a []`.
> **Invariante para depurar** : depois de cada comando completo, a pilha volta à altura que tinha antes.

## 4. Gerando código com BYACC/J — passo a passo
### 4.1 Declarações globais
```code
prog : { geraCod("JMP", "_start"); } decls procs { geraRot("_start"); } BEGIN cmds END '.' { geraCod("HALT"); } ;
decls: decls ID ':' tipo ';'  { declara($2, (Tipo) $4); }  // insere na TS + "_a  DS 4"
```
- `JMP _start` : em uma passagem, dados (`DS`) e procedimentos saem **antes** do principal — sem o salto a máquina executaria dados.
- `integer` → `DS 4` ; `array[5] of integer` → `DS 20`.

### 4.2 Expressões
| Fonte | Código |
|---|---|
| `NUM` | `LDC valor` |
| `ID` | `LDA _x` (global) — o rótulo vem da TS |
| `E1 op E2` | `código(E1) código(E2) OP` |
| `-E` | `código(E) LDC -1 MUL` |
| `(E)` | nada — a ordem já está na estrutura |
| `id := E` | `código(E) STA _x` |
| `a <= b` | `código(a) código(b) GRT LDC 0 EQ` (= não `a > b`) |
| `v[i]` (leitura) | `código(i) LDC w MUL LDC _v ADD LDI` |
| `v[i] := E` | `código(i) LDC w MUL LDC _v ADD código(E) STI` — **endereço antes do valor** |
- Precedência & associatividade : `%left` / `%right` → gramática ambígua sem conflitos.

### 4.3 Comandos de controle
```code
if E then C1 else C2              while E do C
   código de E                    Rn:    NOP
   JZER  Rn                              código de E
   código de C1                          JZER  Rn+1
   JMP   Rn+1                            código de C
Rn:    NOP                               JMP   Rn
   código de C2                   Rn+1:  NOP
Rn+1:  NOP
```
- *"O formato do código não depende do que está dentro de E, C1 e C2."*
- **Aninhamento → pilha `pRot`** : ao abrir, `pRot.push(proxRot); proxRot += 2;` ; durante, `pRot.peek()` e `pRot.peek()+1` ; ao fechar, `pRot.pop()`.
```code
cmd : WHILE      { pRot.push(proxRot); proxRot += 2; geraRot(rot(pRot.peek())); }
      exp DO     { geraCod("JZER", rot(pRot.peek() + 1)); }
      cmd        { geraCod("JMP", rot(pRot.peek())); geraRot(rot(pRot.pop() + 1)); }
    | IF exp THEN { pRot.push(proxRot); proxRot += 2; geraCod("JZER", rot(pRot.peek())); }
      cmd restoIf ;
restoIf : ELSE   { geraCod("JMP", rot(pRot.peek() + 1)); geraRot(rot(pRot.peek())); }
          cmd    { geraRot(rot(pRot.pop() + 1)); }
        | /* vazio */ %prec IFX { geraRot(rot(pRot.pop())); } ;
```
- **Cuidado — ação no meio + prefixo comum = conflito** : `IF exp THEN {A} cmd` e `IF exp THEN {A} cmd ELSE cmd` viram `$$1`/`$$2` vazios → *reduce/reduce*. Solução : **fatorar** (`restoIf`), a mesma técnica da fatoração à esquerda da [P1](./P1.md#46-as-duas-cirurgias).

#### Por que `proxRot += 2`?
- O `if-else` precisa de **dois** rótulos : `Rn` (início do else) e `Rn+1` (fim). `proxRot` = **próximo número de rótulo livre**.
- `pRot.push(proxRot)` guarda a base `n` **deste** comando ; `proxRot += 2` **reserva** `n` e `n+1`, para que comandos aninhados em C1/C2 recebam rótulos novos.
- **Por que não usar `proxRot` direto?** Quando o `ELSE` chega, C1 já foi reconhecido inteiro — se tinha outro `if`/`while`, `proxRot` já andou. A pilha preserva a base de cada comando aberto ; o `pop()` devolve o topo ao comando de fora.
- `if` sem `else` também reserva 2 (só usa `Rn`, `Rn+1` sobra — inofensivo, mantém a ação de abertura única). `while` usa 2 (topo + saída) ; `unless` ([gabarito](#9-gabarito)) só 1 → `+= 1`.

**Rastreando `if a then (if b then x:=1 else x:=2) else x:=3`** (`proxRot = 1`) :

| Momento | Ação | `pRot` | `proxRot` | Emite |
|---|---|---|---|---|
| `THEN` externo | push 1, +2 | [1] | 3 | `JZER R1` |
| `THEN` interno | push 3, +2 | [1, 3] | 5 | `JZER R3` |
| `ELSE` interno | peek = 3 | [1, 3] | 5 | `JMP R4` · `R3: NOP` |
| fim interno | pop → 3 | [1] | 5 | `R4: NOP` |
| `ELSE` externo | peek = 1 | [1] | 5 | `JMP R2` · `R1: NOP` |
| fim externo | pop → 1 | [] | 5 | `R2: NOP` |

#### Pilha semântica × pilha de execução
| | **Pilha semântica** (compilador) | **Pilha de execução** (máquina-alvo) |
|---|---|---|
| **Quando** | tempo de **compilação** | tempo de **execução** |
| **Quem manipula** | o parser (*shift* empilha, *reduce* desempilha) e as ações via `$$`, `$1`… ; `pRot` é uma pilha auxiliar do mesmo tipo | as **instruções geradas** : `LDC LDA ADD STA JZER JSR RTS PUSHBP AMEM`… (x86 : `PUSHL POPL CALL RET`) |
| **Conteúdo** | **atributos** : valor de token, tipo, ref. da TS, base de rótulo | **dados** : operandos intermediários, locais, parâmetros, end. de retorno, BP salvo, resultado de função |
| **Tamanho depende de** | estrutura do **texto** (aninhamento, profundidade da árvore) | comportamento **dinâmico** (recursão, chamadas, expressões) |
| **Um `while`…** | é **compilado 1 vez** → 1 push / 1 pop em `pRot` | pode **executar N vezes** → `JZER` consome a condição a cada volta |
| **Some quando** | a compilação termina — nada vai para o executável | o programa termina — o compilador nunca a "vê", só gera o código que a usa |

> A pilha semântica serve para **escrever** o código ; a de execução é o que o código **usa ao rodar**. `R3` é o número 3 na `pRot` ; no executável vira um endereço fixo — a pilha de execução nunca contém rótulos, só o 0/1 que o `JZER` consome.

#### O rótulo é um endereço?
É um **nome simbólico para um endereço** — não ocupa memória ; no código final é **substituído pelo próprio endereço**.
1. **Compilador** : `R3` é o número 3 na `pRot` ; `rot(3)` gera o texto `"R3"`.
2. **Assembly** : **definição** `R3: NOP` ("R3 = endereço desta instrução") e **uso** `JZER R3`.
3. **Montador** : conta as palavras de cada instrução, anota `R3 → 0x0040` na sua própria tabela de símbolos e troca cada uso pelo número.
4. **Executável** : o nome sumiu — sobra `JZER 0x0040` ; em `0x0040` está o `NOP`.
- Quem ocupa memória é a **instrução marcada** (por isso o `NOP` : dá algo para o rótulo apontar). Usa-se um nome porque, em uma passagem, o compilador ainda não sabe o endereço numérico.
- **Rótulos de dados, mesma ideia** : `_a DS 4` → `_a` = início da área. `LDC _a` empilha o **endereço** (parâmetro `var`) ; `LDA _a` empilha o **conteúdo**.
- **x86** : `_start:`, `_fim_f:` são resolvidos pelo montador (`as`) / *linker* em endereços ; `JMP _fim_f` vira salto numérico.

### 4.4 Subprogramas
```code
proc : PROCEDURE ID          { abreEscopo($2); }                      // nome na TS global (recursão!)
       '(' params ')' ';'    { fixaDeslocParams(); }                  // n conhecido: BP−(n−i+2)
       decls                 { geraRot(rot); geraCod("PUSHBP"); geraCod("SETBP");
                               if (nLocais > 0) geraCod("AMEM", nLocais); }   // prólogo
       BEGIN cmds END ';'    { if (nLocais > 0) geraCod("DMEM", nLocais);
                               geraCod("POPBP"); geraCod("RTS"); fechaEscopo(); } // epílogo
```
**A mesma produção gera código diferente conforme a classe do símbolo na TS :**

| Classe | Leitura `exp → ID` | Atribuição `ID := exp` | Argumento `var` |
|---|---|---|---|
| GLOBAL | `LDA _x` | `código(exp) STA _x` | `LDC _x` |
| LOCAL | `LDO +k` | `código(exp) STO +k` | erro |
| PARAM_VAL | `LDO −k` | `código(exp) STO −k` | erro |
| PARAM_REF | `LDO −k LDI` | `LDO −k código(exp) STI` | `LDO −k` (repassa) |

**Funções** : o chamador reserva o resultado **antes** dos argumentos (`AMEM 1`), a função escreve em `BP−(n+2)`, e depois do `DMEM n` o resultado fica no topo.

### 4.5 A versão x86 do trabalho ([exemploGC](../atividades/exemploGC_inicial_262/README.md))
Mesmo raciocínio, usando a pilha do processador :
```code
8+4*(n-1-i)(%EBP)   parâmetro i (0..n-1)        Prólogo:  PUSHL %EBP · MOVL %ESP, %EBP · SUBL $4m, %ESP
4(%EBP)             endereço de retorno         Epílogo:  _fim_f: MOVL %EBP, %ESP · POPL %EBP · RET
0(%EBP)             %EBP do chamador            Retorno:  POPL %EAX (se houver valor) · JMP _fim_f
-4*k(%EBP)          local k (1..m)              Chamada:  args empilhados · CALL _f · ADDL $4n, %ESP · PUSHL %EAX
```

## 5. Exemplo resolvido — questão 3 da P3 2024/2 (`?:`)
**Esquema** (igual a um `if-else` que deixa um valor na pilha) :
```code
código(Exp1) · JZER Rn · código(Exp2) · JMP Rn+1 · Rn: NOP · código(Exp3) · Rn+1: NOP
```
**Ações :**
```code
%right '?' ':'            // abaixo dos relacionais, acima do '='
...
Exp : Exp '?'   { pRot.push(proxRot); proxRot += 2;
                  System.out.println("JZER " + geraRotulo(pRot.peek())); }
      Exp ':'   { System.out.println("JMP " + geraRotulo(pRot.peek() + 1));
                  System.out.println(geraRotulo(pRot.peek()) + ":NOP"); }
      Exp       { System.out.println(geraRotulo(pRot.pop() + 1) + ":NOP"); }
```
*(É exatamente a solução usada no [`exemploGC.y`](../atividades/exemploGC_inicial_262/exemploGC.y).)*

**Código para `x = a>b ? 3 : 7;`** (supondo `proxRot = 1`) :
```code
        LDA  _a
        LDA  _b
        GRT
        JZER R001
        LDC  3
        JMP  R002
R001:   NOP
        LDC  7
R002:   NOP
        DUP            ; id = Exp : a atribuição também é expressão
        STA  _x
        DROP           ; Cmdo : Exp ;  descarta o valor
```

## 6. Exemplo resolvido — questão 4 da P3 2024/2 (registro de ativação)
- **Quando/por quê** : seção 2.3 — recursão exige uma cópia de parâmetros e locais por ativação.
- **Onde empilhar/desempilhar** :
```code
DeclFun : Tipo IDENT                { insere f na TS global; abreEscopo(); }
          '(' ListaParam ')'        { fixaDeslocParams(); }            // BP−(n−i+2)
          '{' DeclLocais            { geraRot("_" + $2); PUSHBP; SETBP; AMEM nLocais; }
          Cmds '}'                  { "_fim_f:"  DMEM nLocais; POPBP; RTS; fechaEscopo(); }
        ;
Exp : IDENT '('                     { if (f é função) AMEM 1; }          // espaço do resultado
      ArgsOpt ')'                   { JSR _f;  DMEM nArgs; }             // resultado fica no topo
    ;
ArgsOpt  : ListaExp | /* vazio */ ;  // cada Exp de ListaExp já empilha seu valor
```
- **Detalhe que vale ponto** : as duas produções originais `IDENT '(' ')'` e `IDENT '(' ListaExp ')'` com a mesma ação no meio **gerariam conflito** — por isso foram **fatoradas** em `ArgsOpt`. `return e` → `código(e) STO −(n+2)` e salto para `_fim_f`.

## 7. Verificação semântica OO (cai na P3!)
### 7.1 "Classe implementa interface" — o que verificar
Com `class PilhaArrayInt implements IPilhaInt` :
1. `IPilhaInt` existe na TS **e é uma interface** (não classe, não tipo primitivo).
2. Para **cada método** da interface (`push`, `pop`, `empty`), a classe (ou uma superclasse) tem método com :
	- **mesmo nome** e **mesmos tipos de parâmetros, na mesma ordem** (nomes não importam : `val` × `e`);
	- tipo de retorno **igual ou subtipo** (covariância);
	- visibilidade **`public`** (não pode reduzir a da interface).
3. Se falta algum (o `empty()` está em "…") e a classe **não é `abstract`** → **erro**.
4. Registrar `PilhaArrayInt ≤ IPilhaInt` para que `IPilhaInt p = new PilhaArrayInt();` seja aceito.
- **Estruturas** : na TS, entrada da classe com superclasse, **lista de interfaces** e **tabela de métodos** (nome → assinatura : tipos dos parâmetros, retorno, modificadores); a entrada da interface com sua tabela de métodos. A verificação compara as duas tabelas **depois** de ler a classe toda (ou em uma segunda passada).

### 7.2 Genéricos — como tratar
Com `interface IPilha<T> { void push(T v); T pop(); boolean empty(); }` :
1. **Declaração** : `T` é inserido na TS, no escopo da declaração, como **variável de tipo** (com seu limite, se houver : `T extends Comparable<T>`). Dentro do corpo, `T` é um tipo válido mas desconhecido.
2. **Uso** (`IPilha<Integer> p`) : verificar a **aridade** (nº de argumentos de tipo) e se cada argumento **respeita o limite**.
3. **Substituição** : ao verificar `p.push(x)` ou `p.pop()`, substituir `T → Integer` na assinatura : `push(Integer)`, `Integer pop()` → `p.push("a")` é erro; `int x = p.pop()` é OK (unboxing).
4. `class PilhaArray<T> implements IPilha<T>` : as checagens de 7.1 feitas **após a substituição**.
5. Implementação : Java verifica na compilação e **apaga** os tipos (*erasure* → `Object` + casts); C++ **instancia** uma cópia do código por tipo (templates).

> Gabarito na seção 9. Use o conjunto de instruções da seção 3.

**G1 — Expressão à mão.** Gere o código de `z := (a + b) * (a - b) % 4` e execute com `a = 5`, `b = 2`, desenhando a pilha. Qual a altura máxima? Quanto vale `z`?

**G2 — Arranjos.** a) Para `B : array[2..5, 1..3] of integer`, calcule `&B[4,2]`. b) Gere o código de `v[i+1] := v[i] * 2` (`v` global de inteiros).

**G3 — Controle aninhado.** Gere o código (com rótulos) e diga o valor final de `s` para `i = 1`, `n = 6`, `s = 0` :
```code
while i <= n do begin
  if i % 2 = 0 then s := s + i;
  i := i + 1
end
```

**G4 — Comando novo.** Escreva as ações BYACC/J para `unless E do C` (executa `C` só se `E` for **falso**) e o esquema de código.

**G5 — Registro de ativação.** Gere o código do procedimento e da chamada `dobra(g)`, com `g` global (`@500`, valor 7) :
```code
procedure dobra(var x : integer);
  y : integer;
begin
  y := x * 2;
  x := y
end;
```
Desenhe a pilha logo antes do `STI`. Quanto vale `g` no fim?

**G6 — x86 (exemploGC).** Para `int f(int a, int b) { int s; int t; … return s; }` : dê o operando de `a`, `b`, `s`, `t`; escreva prólogo, epílogo e o `return s;`; e gere a chamada em `y = f(3, x);` (`x`, `y` globais).

**G7 — Semântica OO.** Liste os erros semânticos e a verificação que encontra cada um :
```java
interface Forma { double area(); String nome(); }
class Circulo implements Forma { double r; public double area() { return 3.14*r*r; } }
class Quadrado implements Forma { double l; public int area() { return 0; } public String nome() { return "q"; } }
class Caixa<T extends Forma> { T item; void poe(T x) { item = x; } T tira() { return item; } }
// ...
Caixa<Circulo> c1 = new Caixa<Circulo>();
Caixa<String>  c2;

```

**G8 — V/F justificado.**
a) Numa linguagem com recursão, as variáveis locais podem ter endereço fixo (`DS`).
b) `LDA _a · LDA _b · SUB` calcula `b − a`.
c) O link dinâmico aponta para o registro de ativação do chamador.
d) Na passagem por referência, o chamador empilha o valor do argumento.
e) O `JMP _start` no início existe porque dados e procedimentos são emitidos antes do programa principal.

<details><summary>G1</summary>

```code
LDA _a   [5]
LDA _b   [5 2]
ADD      [7]
LDA _a   [7 5]
LDA _b   [7 5 2]     ← altura máxima : 3
SUB      [7 3]
MUL      [21]
LDC 4    [21 4]
MOD      [1]
STA _z   []          z = 1
```
</details>

<details><summary>G2</summary>

a) `&B[4,2] = B + 4·((4−2)·(3−1+1) + (2−1)) = B + 4·(6+1) = B + 28`.
b)
```code
LDA _i  LDC 1  ADD  LDC 4  MUL  LDC _v  ADD      ; endereço de v[i+1]  (primeiro!)
LDA _i  LDC 4  MUL  LDC _v  ADD  LDI             ; valor de v[i]
LDC 2   MUL
STI                                              ; [RT2] := RT1
```
</details>

<details><summary>G3</summary>

`while` usa R001/R002; o `if` (sem else) usa R003 (R004 é reservado mas não emitido) :
```code
R001:  NOP
       LDA _i   LDA _n   GRT   LDC 0   EQ      ; i <= n  =  não (i > n)
       JZER R002
       LDA _i   LDC 2    MOD   LDC 0   EQ
       JZER R003
       LDA _s   LDA _i   ADD   STA _s
R003:  NOP
       LDA _i   LDC 1    ADD   STA _i
       JMP R001
R002:  NOP
```
`s = 2 + 4 + 6 = 12`.
</details>

<details><summary>G4</summary>

Esquema : `código(E) · LDC 0 · EQ · JZER Rn · código(C) · Rn: NOP` (nega E e reaproveita o JZER).
```code
cmd : UNLESS exp DO   { pRot.push(proxRot); proxRot += 1;
                        nega();                         // LDC 0 · EQ
                        geraCod("JZER", rot(pRot.peek())); }
      cmd             { geraRot(rot(pRot.pop())); }
    ;
```
Alternativa sem negar : `JZER` para o corpo e `JMP` para a saída (2 rótulos).
</details>

<details><summary>G5</summary>

`n = 1` → `x` em `BP−2` ; `y` em `BP+1`.
```code
_dobra: NOP
        PUSHBP
        SETBP
        AMEM  1
        LDO   -2      ; endereço de x
        LDI           ; valor de x
        LDC   2
        MUL
        STO   1       ; y := x*2
        LDO   -2      ; endereço de x (para o STI)
        LDO   1       ; y
        STI           ; x := y
        DMEM  1
        POPBP
        RTS
...     LDC   _g      ; var → endereço!
        JSR   _dobra
        DMEM  1
```
Antes do `STI` : `[ 500 | ret | BP ant. || y=14 | 500 | 14 ]`. No fim, **`g = 14`**.
</details>

<details><summary>G6</summary>

`n = 2` : `a` (i=0) → `12(%EBP)` ; `b` (i=1) → `8(%EBP)` ; `s` → `-4(%EBP)` ; `t` → `-8(%EBP)`.
```code
_f:     PUSHL %EBP
        MOVL  %ESP, %EBP
        SUBL  $8, %ESP          ; 2 locais
        ...
        PUSHL -4(%EBP)          ; return s;
        POPL  %EAX
        JMP   _fim_f
_fim_f: MOVL  %EBP, %ESP
        POPL  %EBP
        RET
; y = f(3, x);
        PUSHL $3
        PUSHL _x
        CALL  _f
        ADDL  $8, %ESP          ; tira os 2 argumentos
        PUSHL %EAX              ; resultado como valor da expressão
        POPL  %EDX
        MOVL  %EDX, _y          ; atribuição (gcAtribui)
```
</details>

<details><summary>G7</summary>

1. `Circulo` não implementa `nome()` e não é `abstract` → **erro** (checagem "todos os métodos da interface").
2. `Quadrado.area()` devolve `int`, a interface exige `double` → **retorno incompatível** (primitivos não são covariantes).
3. `Caixa<String>` : `String` não satisfaz o limite `T extends Forma` → **erro de limite do argumento de tipo**.
4. `c1.poe(new Quadrado())` : com `T = Circulo`, a assinatura é `poe(Circulo)`; `Quadrado ≤ Circulo` é falso → **argumento incompatível**.
5. `Forma f = c1.tira()` : `tira()` devolve `Circulo` e `Circulo ≤ Forma` → **OK**.
</details>

<details><summary>G8</summary>

a) **F** — cada ativação precisa da sua cópia; endereços fixos quebram a recursão (FORTRAN antigo não tinha recursão por isso).
b) **F** — calcula `RT2 − RT1 = a − b`.
c) **V** — é o "BP anterior" salvo por `PUSHBP`; o link **estático** é que aponta para o escopo léxico.
d) **F** — empilha o **endereço** (`LDC _a`); o chamado usa `LDI`/`STI`.
e) **V**.
</details>
