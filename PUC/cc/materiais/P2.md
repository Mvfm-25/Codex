## 1. Análise ascendente — a ideia
- **Descendente** : parte de `S` e "adivinha" as produções até chegar nas folhas.
- **Ascendente** : parte das **folhas (tokens)**, reconhece um **handle** (lado direito de uma produção no topo da pilha) e **reduz** para o NT do lado esquerdo, até chegar em `S`.
- Quatro ações :

| Ação | O que faz |
|---|---|
| **shift** `sN` | empilha o próximo token e vai para o estado N |
| **reduce** `rP` | desempilha o lado direito da produção P, empilha o NT e consulta `GoTo` |
| **accept** | `S' → S •` com `$` na entrada |
| **erro** | célula vazia |

- **Conflitos** : *shift-reduce* (pode empilhar ou reduzir) e *reduce-reduce* (duas reduções possíveis). O exemplo clássico de shift-reduce é o **dangling else**.
- **Vantagens** : aceita recursão à esquerda **e** à direita (esquerda é preferível : a pilha não cresce), aceita mais gramáticas que LL(1) — toda LL(1) é LR(1).

## 2. Itens LR(0), closure & goto — passo a passo
- **Item** : produção com um ponto marcando "o quanto já foi visto". `E → E • + T` = já vi `E`, espero `+ T`.
- **closure(I)** : se há `A → α • X β` e `X` é NT, inclua `X → • γ` para toda produção de `X` (e repita).
- **goto(I, X)** : avance o ponto sobre `X` em todos os itens de `I` que têm `• X`, e faça a closure.
- **Construção da tabela** :
	- `goto(Ii, a) = Ij` com `a` terminal → `Action[i, a] = sj`;
	- `goto(Ii, A) = Ij` com `A` não-terminal → `GoTo[i, A] = j`;
	- item completo `A → α •` → reduce : **LR(0)** em **todas** as colunas; **SLR(1)** só nas de `Follow(A)`.

### 2.1 Exemplo resolvido (gramática da [Aula13](../aula13.md))
```code
0  S → E        1  E → E + T      2  E → T      3  T → ( E )      4  T → n
```
**Estados :**
```code
I0: S → •E   E → •E+T   E → •T   T → •(E)   T → •n
I1 = goto(I0,E): S → E•   E → E•+T
I2 = goto(I0,T): E → T•
I3 = goto(I0,( ): T → (•E)   E → •E+T   E → •T   T → •(E)   T → •n
I4 = goto(I0,n): T → n•
I5 = goto(I1,+): E → E+•T   T → •(E)   T → •n
I6 = goto(I3,E): T → (E•)   E → E•+T
I7 = goto(I5,T): E → E+T•
I8 = goto(I6,) ): T → (E)•
```
**Tabela SLR** (`Follow(E) = Follow(T) = {+, ), $}`) :

| | n | + | ( | ) | $ | E | T |
|---|---|---|---|---|---|---|---|
| 0 | s4 | | s3 | | | 1 | 2 |
| 1 | | s5 | | | acc | | |
| 2 | | r2 | | r2 | r2 | | |
| 3 | s4 | | s3 | | | 6 | 2 |
| 4 | | r4 | | r4 | r4 | | |
| 5 | s4 | | s3 | | | | 7 |
| 6 | | s5 | | s8 | | | |
| 7 | | r1 | | r1 | r1 | | |
| 8 | | r3 | | r3 | r3 | | |

**Reconhecendo `n + ( n )` :**

| Pilha | Entrada | Ação |
|---|---|---|
| 0 | n+(n)$ | s4 |
| 0 n 4 | +(n)$ | r4 `T→n` ; goto(0,T)=2 |
| 0 T 2 | +(n)$ | r2 `E→T` ; goto(0,E)=1 |
| 0 E 1 | +(n)$ | s5 |
| 0 E 1 + 5 | (n)$ | s3 |
| 0 E 1 + 5 ( 3 | n)$ | s4 |
| 0 E 1 + 5 ( 3 n 4 | )$ | r4 ; goto(3,T)=2 |
| 0 E 1 + 5 ( 3 T 2 | )$ | r2 ; goto(3,E)=6 |
| 0 E 1 + 5 ( 3 E 6 | )$ | s8 |
| 0 E 1 + 5 ( 3 E 6 ) 8 | $ | r3 `T→(E)` ; goto(5,T)=7 |
| 0 E 1 + 5 T 7 | $ | r1 `E→E+T` ; goto(0,E)=1 |
| 0 E 1 | $ | **accept** |

**Raciocínio padrão** ([Aula16](../aula16.md)) : (1) olhe o estado no topo e o token; (2) shift → empilha e muda de estado; reduce → tira `2×|lado direito|` itens da pilha, empilha o NT e consulta `GoTo` do estado que ficou exposto; (3) repita.

## 3. Adicionando lookahead : SLR(1), CLR(1), LALR(1)
- **LR(0)** reduz sem olhar o próximo token → frágil, muitos conflitos.
- **SLR(1)** : reduz `A → α •` só se o token ∈ `Follow(A)`. Simples, mas `Follow` é global, impreciso.
- **CLR(1) / LR(1) canônico** : cada item carrega seu **próprio lookahead** : `[A → α • β, a]`. Mais preciso, **muitos estados**.
- **LALR(1)** : funde estados CLR com o **mesmo núcleo** (mesmos itens, lookaheads diferentes). Tamanho do LR(0), quase o poder do CLR — o *sweet spot* (é o que **Yacc/BYACC/J** geram). A fusão pode criar conflito **reduce-reduce**, nunca shift-reduce novo.

### 3.1 Algoritmo CLR (o que vem anexo na prova)
1. **Aumente** a gramática : `S' → S`. `I0 = closure({[S' → •S, $]})`.
2. **closure** : para `[A → α • X β, a]` e produção `X → γ`, inclua `[X → • γ, b]` para todo `b ∈ First(β a)`. *(Se `β` é anulável, o `a` original passa adiante.)*
3. **goto(I, X)** : avança o ponto sobre `X`, **mantendo o lookahead**, e faz a closure. Repita para todo estado e símbolo.
4. **Tabela** : goto com terminal → shift; `[S' → S •, $]` → `acc`; `[A → α •, a]` → `reduce` **apenas na coluna `a`**; goto com NT → `GoTo`.

### 3.2 Exemplo resolvido — a questão 2 da P2 2023/1
```code
0  L' → L      1  L → A B      2  A → a A      3  A → ε      4  B → b B      5  B → c
```
`First(A) = {a, ε}` · `First(B) = {b, c}`.

**Passo 1 — I0.** Para `L → • A B, $`, o lookahead dos itens de `A` é `First(B $) = {b, c}` :
```code
I0:  L' → •L, $      L → •A B, $      A → •a A, b/c      A → •, b/c
```
**Passo 2 — os gotos :**
```code
I1 = goto(I0, L): L' → L•, $
I2 = goto(I0, A): L → A•B, $       B → •b B, $       B → •c, $
I3 = goto(I0, a): A → a•A, b/c     A → •a A, b/c     A → •, b/c
I4 = goto(I2, B): L → A B•, $
I5 = goto(I2, b): B → b•B, $       B → •b B, $       B → •c, $
I6 = goto(I2, c): B → c•, $
I7 = goto(I3, A): A → a A•, b/c
     goto(I3, a) = I3   (mesmos itens)
I8 = goto(I5, B): B → b B•, $
     goto(I5, b) = I5 ;  goto(I5, c) = I6
```
**Passo 3 — tabela CLR :**

| | a | b | c | $ | L | A | B |
|---|---|---|---|---|---|---|---|
| 0 | s3 | r3 | r3 | | 1 | 2 | |
| 1 | | | | acc | | | |
| 2 | | s5 | s6 | | | | 4 |
| 3 | s3 | r3 | r3 | | | 7 | |
| 4 | | | | r1 | | | |
| 5 | | s5 | s6 | | | | 8 |
| 6 | | | | r5 | | | |
| 7 | | r2 | r2 | | | | |
| 8 | | | | r4 | | | |

Sem conflitos. *(Note : `A → •` em I0 e I3 vira **reduce de produção vazia** — tira 0 itens da pilha.)*

**Passo 4 — reconhecimento :**

`abc` :

| Pilha | Entrada | Ação |
|---|---|---|
| 0 | abc$ | s3 |
| 0 a 3 | bc$ | r3 `A→ε` ; goto(3,A)=7 |
| 0 a 3 A 7 | bc$ | r2 `A→aA` ; goto(0,A)=2 |
| 0 A 2 | bc$ | s5 |
| 0 A 2 b 5 | c$ | s6 |
| 0 A 2 b 5 c 6 | $ | r5 `B→c` ; goto(5,B)=8 |
| 0 A 2 b 5 B 8 | $ | r4 `B→bB` ; goto(2,B)=4 |
| 0 A 2 B 4 | $ | r1 `L→AB` ; goto(0,L)=1 |
| 0 L 1 | $ | **accept** |

`bc` : `0 | bc$` r3 → `0 A 2` ; s5 ; s6 ; r5 → 8 ; r4 → 4 ; r1 → 1 ; **accept** (n = 0).
`cc` : `0 | cc$` r3 → `0 A 2` ; s6 → `0 A 2 c 6 | c$` : `Action[6, c]` vazia → **erro** (só um `c` é permitido).

## 4. BYACC/J — do `.y` ao parser
### 4.1 Estrutura
```code
%{ imports Java %}
%token NUM ID             // tokens (numerados a partir de 257; '+' vale seu ASCII)
%left '+' '-'             // ordem CRESCENTE de precedência
%left '*' '/'
%right '^'
%%
expr : expr '+' expr      { $$ = new ParserVal($1.ival + $3.ival); }
     | NUM                { $$ = $1; }
     ;
%%
// código do usuário: yylex(), yyerror(), main()
```
- `$$` = atributo do lado esquerdo; `$i` = do i-ésimo símbolo do lado direito. Tudo é `ParserVal` (`ival`, `dval`, `sval`, `obj`).
- `%token <ival> NUM` / `%type <obj> expr` tipam os símbolos → dá pra escrever `$1` direto.
- Ação padrão : `$$ = $1`.
- **Ação no meio da regra** : o BYACC/J cria um **não-terminal vazio** `$$n` naquele ponto → pode gerar conflito se duas produções compartilham o prefixo.
- `error` : `cmd : error ';'` → em erro, desempilha até um estado que aceite `error`, descarta tokens até `;`, reduz e continua (modo pânico pronto).
- Integração com JFlex : `%byaccj` no `.flex`; o léxico preenche `yyparser.yylval = new ParserVal(...)` e devolve `Parser.NUM`.
- Pipeline : `byaccj -J calc.y` → `Parser.java` · `jflex calc.flex` → `Yylex.java` · `javac *.java`.
- **Conflitos não impedem a compilação** : o BYACC/J avisa e resolve sozinho (shift-reduce → **shift**; reduce-reduce → a produção que aparece **primeiro**).

## 5. Tradução Dirigida por Sintaxe — passo a passo
### 5.1 Conceitos
- **SDD (gramática de atributos)** : GLC + atributos nos símbolos + regras semânticas nas produções.
- **Sintetizado** : calculado a partir dos **filhos** (sobe na árvore). `E.val = E1.val + T.val`.
- **Herdado** : calculado a partir do **pai ou irmãos** (desce/anda de lado). `L.inh = T.type`.
- **Árvore anotada** : árvore de derivação com os valores dos atributos em cada nó.
- **Grafo de dependências** → define a **ordem de avaliação** (ordenação topológica).
- **S-atribuída** : só sintetizados → avaliada em pós-ordem → **perfeita para LR** (cada `reduce` calcula `$$`).
- **L-atribuída** : herdados só dependem do pai e dos irmãos **à esquerda** → avaliada numa passada da esquerda para a direita → natural em **ASDR** (herdado = parâmetro, sintetizado = retorno).
- **SDT (esquema de tradução)** : ações `{ }` **embutidas** nas produções, executadas quando o parser passa por ali.

### 5.2 Exemplo — sintetizado (calculadora)
```code
L → E n          { print(E.val) }
E → E1 + T       { E.val = E1.val + T.val }
E → T            { E.val = T.val }
T → T1 * F       { T.val = T1.val * F.val }
T → F            { T.val = F.val }
F → ( E )        { F.val = E.val }
F → digit        { F.val = digit.lexval }
```
Para `3 * 5 + 4 n` : `F=3 → T=3` ; `F=5` ; `T = 3*5 = 15` ; `E=15` ; `F=4 → T=4` ; `E = 15+4 = 19` ; imprime **19**.

### 5.3 Exemplo — herdado (declarações)
```code
D → T L          { L.inh = T.type }
T → int          { T.type = integer }
T → float        { T.type = float }
L → L1 , id      { L1.inh = L.inh ; addType(id.entry, L.inh) }
L → id           { addType(id.entry, L.inh) }
```
Em `float x, y` : `T.type = float` desce para `L.inh`, que desce para `L1.inh`; cada `id` recebe `float`. No BYACC/J, o "herdado" vira o truque do **`$0`** (o valor que está na pilha logo abaixo da regra) ou uma variável global `tipoAtual`.

## 6. Verificação Semântica — passo a passo
### 6.1 Por que a gramática não basta
- *"A gramática aceita um superconjunto da linguagem; a análise semântica filtra os programas sem significado."*
- Exemplos de restrições **fora** da GLC : declarar antes de usar (≈ linguagem `wcw`, não livre de contexto), não redeclarar, tipos compatíveis, número/tipo de argumentos, classe implementa todos os métodos da interface.
- **Validade ≠ correção** : o verificador quer rejeitar o máximo de programas errados, aceitar o máximo de corretos, e ser rápido.

### 6.2 Tabela de símbolos
- Mapeia **nome → (classe/kind, tipo, endereço/deslocamento, parâmetros, …)**.
- Operações : `insere`, `buscaLocal` (só no escopo atual — para detectar **redeclaração**), `busca` (do escopo atual até o global — para **resolver um uso**), `abreEscopo`, `fechaEscopo`.
- Estrutura usual : **pilha de tabelas (hash)**, uma por escopo. O **universo** é o escopo mais externo com os predefinidos (`int`, `true`, `write`…).

### 6.3 Escopos
- **Estático (léxico)** : o uso se liga à declaração **textualmente** mais próxima (C, Java). **Dinâmico** : à ativação mais recente em execução.
- **Ocultação** : um nome local esconde um global igual → aviso (não erro).
- OO : o escopo da subclasse aponta para o da superclasse; a busca segue a **cadeia de herança**.

### 6.4 Tipos
- **Expressões de tipo** : básicos (`int`, `double`, `bool`) e construídos (`array(n, T)`, `T1 × T2 → U`, registros, classes).
- **Regras de inferência** `S ⊢ e : T` (no contexto S, e tem tipo T). Ex.:
```code
S ⊢ e1 : int    S ⊢ e2 : int          S ⊢ e : array(n, T)    S ⊢ i : int
-----------------------------          ------------------------------------
     S ⊢ e1 + e2 : int                          S ⊢ e[i] : T
```
- **Equivalência** : estrutural (mesma forma) × por nome. **Coerção** de alargamento `int → double`. **Subtipos** `≤` (herança).
- **Tipo erro (⊥)** : resultado de uma expressão errada; propaga em silêncio para não gerar **erros em cascata**.

### 6.5 Exemplo resolvido — a questão 3 da P2 2023/1 (protótipos em C)
```code
%token INT DOUBLE VOID ID
%type <obj> tipo
%%
lista_prot : lista_prot prototipo
           | prototipo ;

prototipo  : tipo ID '('          { declaraFuncao($2.sval, (Tipo) $1); }
             params_opt ')' ';'   { ts.fechaEscopo(); }
           ;
tipo       : INT     { $$ = Tipo.INT; }
           | DOUBLE  { $$ = Tipo.DOUBLE; }
           | VOID    { $$ = Tipo.VOID; }
           ;
params_opt : params | /* vazio */ ;
params     : params ',' param | param ;
param      : tipo ID   { declaraParam($2.sval, (Tipo) $1); }
           | tipo      { declaraParam(null,    (Tipo) $1); }   // nome opcional
           ;
```
Rotinas (só a explicação, como pede a questão) :
- `declaraFuncao(nome, tRet)` : `ts.buscaLocal(nome)` no escopo global; se existe → **"função redeclarada"**; senão insere `(nome, FUNCAO, tRet, listaParams = [])`, guarda em `funcAtual` e **abre um escopo** para os parâmetros.
- `declaraParam(nome, t)` : acrescenta `t` à assinatura de `funcAtual`; se `nome ≠ null` : `ts.buscaLocal(nome)` no escopo da função → se existe, **"parâmetro repetido"**; senão insere `(nome, PARAM, t)`.
- `ts.fechaEscopo()` : descarta os nomes dos parâmetros (`int min(int a, int x)` e `int max(int a, int b)` podem repetir `a`).
- A ação no meio (`depois de '('`) não gera conflito porque nenhuma outra regra compartilha o prefixo `tipo ID (`.
