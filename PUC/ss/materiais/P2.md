## 0. Questões que já se repetiram — respostas-modelo
**AES no modo ECB** (P1-exemplo, P1 2026/2 **e** PS 2026/1 — três vezes!)
- *(a) Simétrica* : a **mesma chave secreta** cifra e decifra; rápida, usada para volume de dados; o problema é **distribuir a chave** (por isso existem DH/RSA — seções 3–4).
- *(b) ECB inseguro* : cada bloco é cifrado **independentemente** com a mesma chave → blocos de texto claro iguais geram **blocos cifrados iguais**; padrões vazam (o "pinguim do ECB"), e blocos podem ser reordenados/repetidos sem detecção.
- *(c) Modo melhor* : **CBC** (cada bloco faz XOR com o cifrado anterior, IV aleatório), **CTR** ou, melhor, **GCM** (CTR + autenticação). O encadeamento/contador faz blocos iguais virarem cifrados diferentes.

**Grover × Shor** (P2-exemplo **e** PS) — ver seção 7.

**Superfície × vetor de ataque** (PS; objetiva na P1 2026/2)
- *Superfície* : **o conjunto** de pontos por onde o sistema pode ser atacado (portas, serviços, contas, APIs, pessoas). *Vetor* : **o caminho concreto** usado num ataque (phishing, SQLi numa API, serviço desatualizado).
- Reduzir a superfície = menos lugares para o atacante tentar : menor privilégio, desligar serviços/portas/contas não usados, atualizar.

**Kerckhoffs** (duas P1) : o sistema deve ser seguro **mesmo que tudo, menos a chave, seja público**.

**Pentest** (P2-exemplo e PS) : planejamento/escopo → reconhecimento → varredura & **enumeração** (portas e serviços) → exploração → pós-exploração → relatório.

## 1. Gestão de risco ([Aula17](../aula17.md))
- **Risco = Probabilidade × Impacto.** *Vulnerabilidade* é a fraqueza; *risco* é a chance de ela ser explorada vezes o estrago.
- Níveis **estratégico** (político, decide o que proteger) → **tático** → **operacional** (controles do dia a dia).
- Tríades : **Pessoas, Processos & Tecnologia** e **GRC** (Governança, Risco, Conformidade). O mesmo controle não serve para "a padaria e o banco".
- Receita do convidado : mapear o **ciclo de vida da informação** e, para cada estado, os controles → "90% certo".
- "Risco é infinito, ação é finita" → priorizar pelo produto P × I.

## 2. Aritmética modular — passo a passo ([Aula19](../aula19.md), [Aula20](../aula20.md))
- $Z_n = \{0, 1, …, n-1\}$ — o **anel** dos inteiros módulo n (as listas falam em "anel $Z_n$"); operar e **reduzir mod n**. Ex. em $Z_{12}$ : 9 + 8 = 5, 5 · 7 = 11, 5 − 7 = 10.
- **MDC por Euclides** : divida o maior pelo menor e repita com (divisor, resto) até o resto ser 0; o último resto ≠ 0 é o MDC. Coprimos ⇔ MDC = 1.
- **Inverso** de x em $Z_n$ : y com x · y = 1 (mod n). **Existe ⇔ mdc(x, n) = 1.** Receita (Euclides estendido) :
	1. Faça Euclides entre n e x, guardando os quocientes.
	2. Volte escrevendo cada resto como combinação de n e x, até 1 = n·s + x·t.
	3. O inverso é t mod n.
	- Pseudocódigo dos slides (*ExtendedEuclid*) : `ExtEuclid(x, y)` devolve (d, a, b) com d = mdc(x, y) = a·x + b·y — se y = 0 então `return (x, 1, 0)`, *else* chama `ExtEuclid(y, x mod y)` = (d, a', b') e `return (d, b', a' − ⌊x/y⌋·b')`. O inverso multiplicativo de x mod n é o a (quando d = 1).
- $Z^*_n$ = os elementos invertíveis; $|Z^*_n| = φ(n)$. Para p primo, φ(p) = p − 1; para n = p·q, φ = (p−1)(q−1).
- **Fermat** (p primo) : $x^{p-1} = 1$ em $Z_p$ → reduza o expoente **mod (p − 1)**. Inverso alternativo : $x^{-1} = x^{p-2}$.
- **Euler** (qualquer n, mdc(x,n) = 1) : $x^{φ(n)} = 1$ → reduza o expoente **mod φ(n)**. É a **generalização** de Fermat (para n = p primo, φ(p) = p − 1).
- **Ordem** de g, $ord_p(g)$ : o menor k > 0 com $g^k = 1$ em $Z_p$ (ex. $ord_7(2) = 3$, pois 2³ = 8 = 1; $ord_7(3) = 6$). A ordem sempre divide p − 1, e **g é gerador ⇔ $ord_p(g) = p − 1$**.
- **Gerador** g de $Z^*_p$ : suas potências $g^0 … g^{p-2}$ percorrem todo $Z^*_p$ (ordem de g = p − 1). $Z^*_p$ é **cíclico** (sempre tem gerador).
- **Pano de fundo** (slides) : N inteiro positivo, p primo, $Z_N$ com soma e produto mod N; números compostos se fatoram de um único jeito, mas **fatorar é difícil** — base do RSA.
- **Equações lineares** em $Z_N$ : $a·x + b = 0$ tem solução $x = −b·a^{-1}$ quando mdc(a, N) = 1. Ex. em $Z_7$ : 3x + 2 = 0 → x = −2·3⁻¹ = 5·5 = 25 = **4** (3·4 + 2 = 14 = 0 ✔).
- **Fermat (1640) e a geração de primos** : sorteie p de n bits e teste $2^{p-1} = 1$ (mod p); se falhar, p é composto com certeza; se passar, p é primo com altíssima probabilidade (ensaio usado para gerar as chaves do RSA).
- *Leia expoentes com cuidado nas listas* : "2¹⁰ em Z₇" aparece no PDF como "210 em Z7".

## 3. Troca de chaves
**Meta** : Alice e Bob combinarem uma chave que um **espião** (que só escuta, não altera) não descubra. Dá para fazer só com criptografia simétrica? **Sim, mas de forma ineficiente.**

**Quebra-cabeças de Merkle (1974)** — receita :
1. Alice prepara n = 2³² puzzles : para cada i sorteia $P_i$ (32 bits), $x_i$ e $k_i$ (128 bits) e faz $puzzle_i = E(0^{96} ‖ P_i, \text{"Puzzle \#" } x_i ‖ k_i)$ — cada um se resolve testando 2³² chaves.
2. Envia todos a Bob; Bob escolhe **um** ao acaso, resolve, obtém $(x_j, k_j)$ e devolve $x_j$ em claro.
3. Alice localiza o puzzle $x_j$; os dois usam $k_j$.
- Trabalho : Alice O(n), Bob O(n), **espião O(n²)** (≈ 2⁶⁴) — uma diferença só **quadrática**, e é o melhor possível tratando a cifra como caixa-preta [IR'89, BM'09]; para algo melhor precisamos de problemas algébricos (DH).

**Diffie-Hellman** (assimétrico) — receita :
1. Públicos : primo p e gerador g de $Z^*_p$.
2. Alice sorteia a, envia $A = g^a \bmod p$; Bob sorteia b, envia $B = g^b \bmod p$.
3. Alice calcula $K = B^a$, Bob $K = A^b$ — ambos dão $g^{ab} \bmod p$.
4. O espião vê p, g, A, B; calcular $DH_g(g^a, g^b) = g^{ab}$ exige o **logaritmo discreto** (difícil para p grande — o slide sugere ~600 dígitos).
- **Fraqueza** : não autentica ninguém → **man-in-the-middle** troca A e B pelos seus e negocia uma chave com cada lado. Solução : autenticar as chaves públicas (assinatura digital, certificados).

## 4. RSA — passo a passo (slides do prof. Avelino)
1. Escolha primos p, q; **N = p·q**; **φ(N) = (p−1)(q−1)**.
2. Escolha **e** com 1 < e < φ(N) e mdc(e, φ(N)) = 1.
3. **d = e⁻¹ mod φ(N)** (Euclides estendido).
4. Pública **PK = {e, N}**; privada **SK = {d, p, q}**.
5. Cifrar : $C = M^e \bmod N$ (M < N). Decifrar : $M = C^d \bmod N$.

Exemplo dos slides : p = 5, q = 11 → N = 55, φ = 40, e = 7, d = 23 (7·23 = 161 = 4·40 + 1); M = 8 → C = 8⁷ mod 55 = 2 → 2²³ mod 55 = 8.
- **Por que funciona** : e·d = 1 + k·φ(N) e, por Euler, $M^{φ(N)} = 1$ → $C^d = M^{1+kφ} = M$.
- **Segurança** : fatorar N. **Atenção à notação** : nos slides de *assinatura* (prof. Edson, a partir de Diego Aranha) a pública é **b** e a privada **a** — é o mesmo esquema com outros nomes.

## 5. Curvas elípticas — passo a passo ([Aula22](../aula22.md))
- Curva $y^2 = x^3 + ax + b \pmod p$ com $4a^3 + 27b^2 \ne 0$, mais o ponto no infinito **θ (ou O)**, identidade do grupo. Inverso de T = (x, y) é −T = (x, −y).
- **Soma R = T + U** :
	- $S = (y_U − y_T)·(x_U − x_T)^{-1}$ se T ≠ U; $S = (3x_T^2 + a)·(2y_T)^{-1}$ se T = U (duplicação);
	- $x_R = S^2 − x_T − x_U$; $y_R = S(x_T − x_R) − y_T$ (tudo mod p).
	- Exemplo dos slides : $y^2 = x^3 + 2x + 2$ mod 17, T = (5,1) → S = 77·2⁻¹ = 13 → **2T = (6, 3)**.
- **k·P por double-and-add** : escreva k em binário; comece com P no 1º bit; para cada bit seguinte **dobre**, e se o bit for 1 **some P**.
- **ECDH** : Alice publica A = aP, Bob B = bP; segredo comum a·B = b·A = abP. Segurança : logaritmo discreto em curvas.
- **Grupo cíclico e ordem** : no exemplo $y^2 = x^3 + 2x + 2$ mod 17, T = (5, 1) gera **19 pontos** (… 10T = (7, 11), …, 19T = θ) → #E = 19. **Teorema de Hasse** : $p + 1 − 2\sqrt{p} ≤ \#E ≤ p + 1 + 2\sqrt{p}$ → o número de pontos é "próximo" de p; para um grupo de ~2¹⁶⁰ pontos, p de ~160 bits.
- **ECDLP** : dados T e U = dT, achar d (1 ≤ d ≤ #E). Fácil calcular dT (double-and-add); difícil voltar.
- **Double-and-add do slide** : U = 26T, 26 = 11010₂ → T → (dobra + soma) 3T → (dobra) 6T → (dobra + soma) 13T → (dobra) **26T** — 4 duplicações e 2 somas em vez de 25 somas. *(Na curva do slide, 26T = 7T = (0, 6), pois a ordem é 19.)*
- **ECDH na prática** : Alice e Bob calculam $T_{AB} = abP$ e usam **uma coordenada** como segredo; deriva-se a chave AES de sessão e **c = AES_K(msg)**. Esquema híbrido : o servidor publica a chave EC; o cliente cria uma chave de sessão aleatória, cifra a mensagem com AES e a chave de sessão com a pública EC; o servidor decifra a chave de sessão com a privada e depois a mensagem.
- **Implementação** : 4 camadas (aritmética modular → soma/duplicação de pontos → multiplicação D&A → protocolo ECDH); o gargalo é a **inversão modular**. Software 256 bits ≈ 2 ms numa CPU de 3 GHz (>10 ms em smartcard/celular); FPGA centenas de µs; ASIC dezenas de µs.
- **RSA × EC** (NIST SP 800-57) :

| Nível | RSA | EC |
|---|---|---|
| básico | 1024 | 160 |
| alto | 2048 | 224 |
| forte | 3072 | 256 |
| altamente sensível | 7680–15360 | 384–512 |
- **Por que curvas?** Mesma segurança com chaves **muito menores** → menos memória e CPU (cartões, IoT, celular — o WhatsApp usa Curve25519).

## 6. Assinatura digital ([Aula24](../aula24.md))
1. Remetente calcula **h = H(m)** (ex. SHA-256).
2. Assina com a **chave privada** : $s = h^d \bmod N$.
3. Envia (m, s). Destinatário recalcula H(m) e verifica $s^e \bmod N = H(m)$ com a **chave pública**.
- Garante **integridade, autenticidade e não-repúdio** (só o dono da privada assina). Desvantagem : mensagem maior e custo de gerar/verificar.
- **Por que assinar o hash** : tamanho fixo e pequeno (< N), rápido, e a assinatura cobre a mensagem inteira.
- **MAC × assinatura** : MAC usa **chave compartilhada** → não dá não-repúdio (os dois lados poderiam ter gerado). Assinatura usa par de chaves.
- Notação dos slides (prof. Edson / D. Aranha) : $K = (N, p, q, a, b)$, pública **(b, N)**, privada **(a, N, p, q)**; assina $s = m^a \bmod N$ e verifica $m ≡ s^b \bmod N$ — aplicações : documentos do governo, contratos de comércio eletrônico, e-mail, distribuição de software (e a urna do TSE, [Aula14](../aula14.md)).

**Lista de assinatura digital, resolvida** ([enunciado](../atividades/AssinaturaDigital.pdf), [chave pública](<../atividades/Chave Publica.txt>), [chave privada](<../atividades/Chave Privada.txt>), [Exec1](../atividades/AssinaturaDigital_Exec1.txt), [Exec2](../atividades/AssinaturaDigital_Exec2.txt), [sua resolução](../atividades/resolucaoAssinaturaDigital.md))
- **Ex. 1** : SHA-256 da mensagem → RSA com a chave do par gerado. Como o site usa padding aleatório, cada execução dá uma etiqueta diferente (as suas para "Tênis" e "Poste" estão na sua resolução).
- **Ex. 2** : decifrando com a privada (RSA-2048, e = 65537) : Exec1 → `cbe0220b…cffc860` = **SHA-256("Primeiro")** ✔; Exec2 → `71029cbf…6a8d800e` = **SHA-256("Ultimo")** ✔ (trocadas, não conferem). Conferido com `cripto_calc.py rsa-pem`.
- ⚠ **Observação conceitual** : o bloco decifrado tem padding PKCS#1 **tipo 2** (de *cifragem*) — as etiquetas foram produzidas **cifrando o hash com a chave pública**, por isso "precisa usar a privada" para verificar. Numa assinatura de verdade é o contrário : **assina-se com a privada** (padding tipo 1/PSS) e **qualquer um verifica com a pública** — senão não há não-repúdio (quem tem a pública poderia ter gerado a etiqueta).
- **Ex. 3 — MITM** : (1) se a chave pública chega por canal inseguro, o atacante entrega a **dele**, troca a mensagem e "assina" no lugar; também pode reenviar uma mensagem antiga assinada (*replay*). (2) Mitigações : **certificados** de uma autoridade (ICP/CA) ou conferência da impressão digital da chave fora de banda, **assinar com a privada** (não cifrar com a pública), incluir **timestamp/nonce** contra replay e transportar por canal autenticado (TLS).

## 7. Criptografia pós-quântica ([Palestra-PQC](../atividades/Palestra-PQC.pdf))
- **Grover** : busca não estruturada com ganho **quadrático** → força bruta em chave de n bits custa $2^{n/2}$. Ameaça a **simétrica e hashes**, mas a contramedida é simples : **dobrar o tamanho** (AES-128 → AES-256).
- **Shor** : resolve **fatoração e logaritmo discreto** em tempo polinomial → **quebra RSA, DH e ECC** (recupera a chave privada). Sem contramedida simples → migrar para algoritmos **PQC**.
- **Resposta-modelo** "Grover ameaça simétrica e/ou assimétrica?" : ameaça principalmente a **simétrica** (e hashes), reduzindo pela metade a segurança efetiva, resolvível dobrando a chave; a assimétrica é ameaçada pelo **Shor**, não pelo Grover.
- **Computação quântica** : superposição, emaranhamento, tunelamento, interferência; qubits (supercondutores, íons aprisionados, fotônicos, spin, topológicos) **muito sensíveis a ruído** → correção de erros, qubits físicos × lógicos, limite de escala.
- **CRQC** (computador quântico criptograficamente relevante) : milhares de qubits **lógicos** (milhões de físicos), tolerância a falhas, fidelidade e profundidade de circuito. Estimativas : 2029 (IBM, Google, Gartner); 28–49% até 2035, 51–70% até 2040.
- **Harvest Now, Decrypt Later (HNDL)** : guardar cifrados hoje para decifrar depois → migrar já. EUA/UE : infraestrutura crítica até **2030**, migração total até **2035** (estimativa de 10–20 anos para migrar).
- Detalhe do Grover (IETF) : operações quânticas são **sequenciais** (as clássicas paralelizam) → na prática **nem sempre é preciso dobrar** a chave; dobrar é a margem conservadora.
- **PQC** : baseada em **outros problemas matemáticos**, resistente a ataques clássicos e quânticos, **roda em computador clássico**. Padronização do **NIST** desde 2016 : 59 KEMs + 23 assinaturas submetidos → 4 rodadas.
- **Níveis de segurança do NIST** : 1 ≈ busca de chave em cifra de bloco de 128 bits · 2 ≈ colisão em hash de 256 · 3 ≈ cifra de 192 · 4 ≈ hash de 384 · 5 ≈ cifra de 256.
- **Famílias** : **reticulados** (vetor mais curto numa grade multidimensional), **hash**, **códigos** (decodificar com ruído), **isogenias** (caminho entre curvas elípticas), **multivariadas** (sistemas polinomiais), MPC-in-the-head.
- **Selecionados** : **ML-KEM (Kyber)**, **ML-DSA (Dilithium)**, **FN-DSA (Falcon)** — reticulados; **SLH-DSA (SPHINCS+)** — hash sem estado; **HQC** — códigos; XMSS e LMS — hash com estado.
- **Sistemas afetados** : TLS, VPNs, blockchains, WhatsApp → migrar, com custo de desempenho e armazenamento. Pesquisa da palestrante (PQCinBlock, 46 variantes) : no mesmo nível, o **ECDSA** ainda é mais rápido para gerar chaves e assinar; os PQC têm chaves/assinaturas maiores.

## 8. Blockchain ([Aula25](../aula25.md))
- **Bitcoin ≠ blockchain** : o Bitcoin é uma criptomoeda que **usa** uma blockchain.
- Ingredientes : criptografia assimétrica (usuários = chaves públicas), **lista encadeada** (cada bloco guarda o hash do anterior), função hash, **assinatura digital** (transações), rede **P2P**, **Merkle tree** (raiz resume as transações).
- **Header** : versão, hash do bloco pai, raiz Merkle, timestamp, **nBits** (dificuldade), **nonce**.
- **Proof of Work** : achar um nonce tal que o hash do header tenha a dificuldade pedida → adicionar blocos é **caro**, alterar o passado exige refazer o trabalho de todos os blocos seguintes.
	- Desvantagens : **gasto de energia** enorme, lentidão, concentração em quem tem mais hardware, risco de **ataque de 51%**.
- **Proof of Stake** : quem tem **mais moedas (ou mais antigas)** tem mais chance de criar o bloco.
	- Desvantagens : **"rico fica mais rico"** (centralização), *nothing at stake* (validar forks sem custo), exige mecanismos de punição.
- **PBFT** : um líder por rodada valida com os nós (problema dos generais bizantinos).
- **Rede** : todo nodo tem uma cópia da blockchain e pode pedir transações pela P2P; o **minerador** também cria blocos com as transações recebidas, garante a integridade dos blocos dos outros e é recompensado.
- **Bloco** = **header** (Block Version, **Parent Block Hash**, **Merkle Tree Root**, Timestamp, nBits, Nonce) + **data** (as transações). Encadeamento a partir do bloco **gênesis**.
- **Bitcoin** = livro-razão : cada usuário é uma **chave pública**; cada transação aponta a origem das moedas e é **assinada pelo dono anterior** — na transação seguinte verifica-se a posse e o novo dono assina.
- **Inserção** : o minerador junta transações num bloco. Problema : quem decide qual bloco entra? → **algoritmos de consenso**.
- **PoW (exemplo do slide)** : com nBits = 16, o nonce 0 não serve; o minerador incrementa até o nonce **531** dar um hash começando com `00…`; o bloco vai para a rede, os outros nodos verificam, e os mineradores disputam quem acha primeiro.
- **Problemas** : uso para atividades ilegais (Silk Road), **forks**, conteúdo impróprio gravado para sempre, exploits de **smart contracts**.
- **badHash da Candycoin** : XOR de 01010101 com todos os bytes. Exemplo do slide : 01010101 ⊕ 10010001 = 11000100; ⊕ 00000010 = **11000110**. *(A dinâmica em aula usou blocos de 1 byte por campo e no máximo 2 transações.)*

**Perguntas do fim dos slides ("vale Candycoins") — respondidas** *(a 2ª caiu na P2-exemplo)*
1. *"Quanto maior a blockchain, maior a segurança contra adulterações"?* **Em geral sim** : alterar um bloco exige refazer o PoW dele e de **todos os seguintes** mais rápido que a rede inteira — quanto mais blocos depois dele, mais caro. Mas o que garante é o **poder de processamento honesto**, não o tamanho em si (uma cadeia longa com pouca mineração continua frágil).
2. *Desvantagens de PoW e PoS?* Seção 8 (energia/centralização em mineradores/51% × concentração em quem tem mais moedas/*nothing at stake*).
3. *Uma transação pode ser retirada?* Não se pode apagar um bloco confirmado, mas uma transação some se estiver num bloco que perde um **fork** (cadeia órfã) ou num **ataque de 51%** — por isso esperam-se várias confirmações (≈ 6 blocos).
4. *Rede P2P dividida em duas e depois reunida?* Cada parte segue minerando a sua cadeia → **fork**; ao reunir, vale a cadeia com **mais trabalho acumulado** (a mais longa); os blocos da outra viram órfãos e suas transações voltam ao pool.
5. *Um minerador com mais poder que o resto da rede?* **Sim** : com > 50% do hash ele faz **ataque de 51%** — reescreve o histórico recente, gasta duas vezes (*double spending*) e censura transações (não consegue roubar moedas sem a chave privada).

## 9. WhatsApp / protocolo Signal
- **E2EE** desde 2016 : só as pontas decifram; nem o servidor lê.
- Chaves públicas (Curve25519) : **Identity Key** (longo prazo, identifica o usuário) · **Signed Pre Key** (médio prazo, **assinada pela IK** — prova que é do dono) · **One-Time Pre Keys** (uso único, consumidas no início de cada sessão e **apagadas do servidor** para que nenhuma seja reutilizada).
- **X3DH** combina essas chaves para criar a chave inicial mesmo com o destinatário offline.
- **Double Ratchet** = **hash ratchet** (cada mensagem deriva a próxima chave por função unidirecional) + **DH ratchet** (novo ECDH a cada troca de turno) → **sigilo futuro** (vazar a chave de hoje não revela mensagens antigas) e **sigilo pós-comprometimento** (o DH novo "cura" a sessão).
- Primitivas : AES-256, HMAC-SHA256, Curve25519 (curva $y^2 = x^3 + 486662x^2 + x$ mod $2^{255} − 19$, menos sensível a geradores aleatórios fracos).
- **Chaves de sessão** (simétricas) : **Root Key** (32 bytes, ponto de partida) → **Chain Key** (renovada a cada mensagem) → **Message Key** (80 bytes : 32 AES-256 + 32 HMAC-SHA256 + 16 de IV).
- **Instalação** : o cliente gera IK, SPK (assinada) e um lote de OTPK; o servidor guarda **só as públicas** — o WhatsApp **não tem as privadas**.
- **Estabelecimento de sessão (iniciador)** :
	1. pede ao servidor $I_{rec}$, $S_{rec}$, $O_{rec}$ do destinatário (a OTPK é removida do servidor após o uso) e verifica a identidade;
	2. salva as chaves, gera um par **efêmero** $E_{ini}$ (Curve25519) e carrega sua $I_{ini}$;
	3. `master_secret = ECDH(I_ini, S_rec) ‖ ECDH(E_ini, I_rec) ‖ ECDH(E_ini, S_rec) ‖ ECDH(E_ini, O_rec)`;
	4. **HKDF** → Root Key e Chain Key; já pode enviar mesmo com o destinatário **offline**, mandando $E_{ini}$ e $I_{ini}$ no cabeçalho.
- **Destinatário** : calcula o mesmo master_secret com as suas privadas, **apaga a OTPK usada** e deriva as mesmas chaves (a sessão dura até reinstalar ou trocar de aparelho).
- **Troca de mensagens** : cada mensagem com Message Key **única** — **AES-256-CBC + HMAC-SHA256**.
	- **Hash ratchet** (ao enviar) : `MK = HMAC-SHA256(CK, 0x01)` e `CK = HMAC-SHA256(CK, 0x02)` → uma MK vazada não revela CKs atuais nem passadas.
	- **DH ratchet** (ao receber) : `ephemeral_secret = ECDH(E_ini, E_rec)`; `CK, RK = HKDF(RK, ephemeral_secret)`.
- **Mídia** : o remetente gera chave AES-256 e chave HMAC efêmeras, cifra o anexo (CBC, IV aleatório) + HMAC, envia o **BLOB** cifrado ao servidor de BLOBs e manda ao destinatário, numa mensagem normal, a chave, o HMAC, o SHA-256 do BLOB e o ponteiro; o destinatário baixa, confere o hash e decifra.
- **Contra ataques conhecidos** : **MITM** (verificação de chaves, assinaturas Ed25519, Double Ratchet) · **replay** (chaves efêmeras distintas e descartadas) · **comprometimento de chave** por malware/root/backup (limitado : chave por mensagem + ratchet que renova + sigilo futuro).
- **As duas perguntas do professor** ([lista](../atividades/SS___Perguntas_protocolo_Whatsapp.pdf)) : (1) *Double Ratchet e sigilo futuro* — o hash ratchet é unidirecional (não se volta à chave anterior), então vazar a chave atual não revela mensagens passadas; o DH ratchet injeta segredo novo a cada troca de turno, então o atacante perde o acesso assim que um novo ECDH acontece (sigilo pós-comprometimento) e o dano fica limitado a poucas mensagens. (2) *IK, SPK, OTPK* — IK identifica o usuário a longo prazo; SPK, de médio prazo e **assinada pela IK**, prova a autenticidade e permite a sessão offline; OTPK é efêmera e **removida após o uso** para que cada sessão inicial tenha um segredo exclusivo (sem reutilização = sem replay e com sigilo futuro desde a primeira mensagem).
